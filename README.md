# ClutchD — Backend

Production-oriented FastAPI service for the **ClutchD** on-demand mechanic platform. It mirrors the API shape expected by the frontend (`/api` prefix, `/auth/signup`, `/service/request`, `/providers/nearby`, WebSocket at `/ws`) and adds the full spec: PostGIS matching, Redis, Celery, Stripe/Razorpay hooks, admin APIs, and job-scoped WebSockets.

## Stack

- **FastAPI** (async) + **Pydantic v2**
- **PostgreSQL + PostGIS** (geography distance queries)
- **Redis** (pricing multiplier cache; optional pub/sub extension point)
- **Celery** (retry job assignment, notification stub)
- **JWT** auth, **bcrypt** passwords, optional **Google ID token** login
- **WebSockets**: `GET ws://host/ws?token=...` (user channel + mechanic location updates) and `ws://host/ws/tracking/{job_id}?token=...`

## Quick start (Docker)

From this directory:

```bash
docker compose up --build
```

- REST: `http://localhost:8000/api/...`
- Health: `http://localhost:8000/health`
- OpenAPI: `http://localhost:8000/docs`

The API container runs `scripts/bootstrap_db.py` on start (creates PostGIS + tables + seed users if missing).

### Worker (Celery)

The Celery worker is **disabled by default** (restart policy: `"no"`). It processes background tasks such as job assignment retries and notifications.

```bash
# Start the worker
docker compose up -d worker

# Stop the worker
docker compose stop worker

# View worker logs
docker compose logs -f worker
```

The API works without the worker — tasks simply queue in Redis until the worker is running again.

## Local development (without Docker)

1. Install PostGIS locally and create DB `clutchd` (or adjust URLs).
2. `cd backend && python -m venv .venv && source .venv/bin/activate`
3. `pip install -r requirements.txt`
4. Copy `.env.example` to `.env` and edit.
5. `python scripts/bootstrap_db.py`
6. `uvicorn app.main:app --reload --host 0.0.0.0 --port 8000`
7. Celery (optional): `celery -A app.tasks.worker.celery_app worker --loglevel=info`

### Frontend env

Point the Next app at this API:

- `NEXT_PUBLIC_API_URL=http://localhost:8000/api`
- `NEXT_PUBLIC_WS_URL=ws://localhost:8000/ws`

Uploaded files are served under `http://localhost:8000/static/uploads/...` (set full URL in the client if needed).

## Database Migrations

Alembic manages schema changes. All migration files live in `backend/migrations/versions/`.

**Prerequisites:** Set `DATABASE_URL` (and `SYNC_DATABASE_URL`) as environment variables, or use the Docker defaults in `alembic.ini`. The `env.py` overrides the connection URL from `DATABASE_URL` if the env var is set, which covers Docker, Render, and local dev automatically.

### Workflow — after changing a model

```bash
# 1. Auto-generate a migration from your model changes
cd backend && bash scripts/makemigration.sh "add service_category to Job"

# 2. Review the generated file in migrations/versions/
#    Make sure upgrade() does what you expect and downgrade() reverts cleanly.

# 3. Apply it to your local database
cd backend && bash scripts/migrate.sh
```

> **Tip:** `makemigration.sh` accepts an optional message argument. If omitted, it defaults to `"autogenerated migration"`.

### Apply pending migrations only

```bash
cd backend && bash scripts/migrate.sh
```

### Manual rollback

```bash
cd backend && PYTHONPATH=. alembic downgrade -1   # back one revision
cd backend && PYTHONPATH=. alembic downgrade <revision_id>  # to a specific revision
```

### How it works

- `bootstrap_db.py` auto-stamps the Alembic head when it creates tables, so fresh databases stay in sync.
- The `env.py` picks up `DATABASE_URL` automatically — no need to edit `alembic.ini` per environment.
- All existing migrations are already in `migrations/versions/`.

## API map (high level)

| Area | Paths |
| --- | --- |
| Auth | `POST /api/auth/login`, `/signup`, `/register/customer|mechanic|garage`, `/oauth/google`, `/logout` |
| Service (frontend) | `POST /api/service/request`, `PATCH .../status`, `POST .../complete`, `POST .../cancel` |
| Jobs (spec) | `POST /api/jobs/create`, `POST /api/jobs/assign`, `GET /api/jobs/status/{id}` |
| Matching | `GET /api/mechanics/nearby`, `/api/garages/nearby`, `GET /api/providers/nearby` |
| Garage | `POST /api/garage/add-mechanic`, `GET /api/garage/mechanics` |
| Reviews | `POST /api/reviews`, `GET /api/ratings/{entity_id}?entity_type=mechanic\|garage` |
| Payments | `POST /api/payments/create`, `POST /api/payments/verify` |
| Admin | `GET /api/admin/users`, `PATCH .../mechanics/{id}/verify`, `PATCH .../garages/{id}/verify`, analytics, disputes, pricing (Redis) |
| Uploads | `POST /api/uploads` (multipart) |

## Security notes

- Set a strong `JWT_SECRET_KEY` in production.
- Configure `CORS_ORIGINS` explicitly.
- Stripe/Razorpay keys are optional until you enable payments.
- Change seed passwords before any shared deployment.

## Layout

```
backend/
  app/
    main.py           # FastAPI app, CORS, static uploads, WebSockets
    api/v1/           # Routers
    core/             # config, security, limiter, redis
    db/               # async engine + session
    models/           # SQLAlchemy models
    schemas/          # Pydantic
    services/         # auth, jobs, matching
    tasks/worker.py   # Celery app + tasks
    ws/manager.py     # WebSocket fan-out
  scripts/
    bootstrap_db.py   # Creates tables + seeds demo data
    makemigration.sh  # Auto-generate Alembic migration
    migrate.sh        # Apply pending migrations
  migrations/         # Alembic configuration + version scripts
    env.py            # Reads DATABASE_URL automatically
    versions/         # Generated migration files
  requirements.txt
  Dockerfile
  alembic.ini
docker-compose.yml
```

The frontend project is **not** modified here; it remains the reference for request/response shapes.
